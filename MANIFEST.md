| `.cta-footer-fixed` | **Nuevo** — variante `position:fixed` (no `absolute`) de `.cta-footer`, para pantallas donde ningún ancestro es `position:relative/absolute/fixed` (el flujo de reserva: `s4`, `s-pago` — `.pantalla`/`.card`/`.contenedor` son todos `static`, así que acá `.cta-footer` con `absolute` no serviría, se ancla al final del documento en vez del viewport). `left:50%;transform:translateX(-50%);max-width:523px` en vez de `left:0;right:0` — centra el footer respetando el ancho de columna de `.contenedor` (`max-width:427px` + `2×48px` de margen visual) en vez de ir de borde a borde como `#home-nav`. Aplicada en `#s4` (envuelve `#btn-s4-continuar`) y en `#s-pago` (envuelve `.chk-pago-label` + `#err-pago` + `#btn-pago` juntos — son una unidad de interacción: el checkbox habilita el botón y `err-pago` es su error de validación; `#btn-wp-pago`, el link de WhatsApp, queda fuera a propósito, en el contenido scrolleable, por no ser parte de esa unidad). El spacer de `s-pago` necesita `style="height:200px"` inline (no el `80px` base de `.cta-footer-spacer`) porque su footer mide ~191px real (3 elementos apilados) contra los ~76px del de `s4` (un solo botón) — medido con Playwright antes de decidir el valor. **2 bugs reales encontrados y corregidos para que `position:fixed` funcionara acá** (ninguno tocaba `s4`/`s-pago` hasta ahora porque nadie había anidado antes un `position:fixed` dentro de una `.pantalla`): **(1)** `@keyframes smoothSlideUp` (`to { transform: translateY(0) }`) + `.pantalla.activa { animation: ... forwards }` — con `forwards`, el navegador trata al elemento como "bajo un efecto de animación activo sobre `transform`" durante todo el fill-forward (no solo mientras la animación corre), y eso alcanza para que se establezca containing block para descendientes `position:fixed`/`absolute`, sin importar que el valor final sea `translateY(0)` (equivalente visualmente a "sin transform" pero no es la palabra clave `none`). Confirmado con un harness aislado: cambiar el keyframe a `transform:none` **no alcanza** por sí solo mientras exista `forwards` — el fix real fue sacar `forwards` de `.pantalla.activa` (innecesario: el valor final de la animación ya coincide con el estado sin animar de `.pantalla`, `opacity:1`/`transform:none` por cascada, así que no hay salto visual al quitarlo). **(2)** `.card` tiene `backdrop-filter:var(--card-blur)` (resuelve a `blur(16px)`) en su regla base — un `backdrop-filter` distinto de `none` también establece containing block para `position:fixed`/`absolute`, y el override de `.card` en mobile (`ui.css`, `@media max-width:600px`) nunca lo resetea (solo saca `background`/`border`/`box-shadow`/`border-radius`/`padding`). Confirmado con `element.offsetParent` (debía ser `null` para un `position:fixed` real; daba `DIV.card`). Fix: `#s4 .card, #s-pago .card { backdrop-filter:none; -webkit-backdrop-filter:none; }` en `estilos.css`, acotado a estas 2 pantallas — no se tocó `.card` globalmente para no afectar el efecto frosted-glass en el resto de la app. Verificado con Playwright (`offsetParent===null`, posición idéntica antes/después de scrollear al fondo del documento, contenido real no tapado por el footer) en ambas pantallas |

Dark mode: `.loading-card`/`.loading-card p` en `@media (prefers-color-scheme: dark)` al final del archivo (antes en `login.css`).

**Lo que se dejó fuera a propósito** (específico de una sola sección, no genérico): `@keyframes smoothSlideDown` (`nav.css`, solo `.app-nav-sticky`), `@keyframes unlockForm` y `@keyframes dpFadeIn` (`inscripcion.css`, únicas de esa página — el date picker compartido no tiene su CSS centralizado, es un sistema aparte no cubierto por esta fase), `@keyframes fadeInUp` (`login.css` — **código muerto, no la usa ningún selector**, se dejó intacta por no ser parte del pedido).

- **css/estilos.css + js/home.js** — 2 bugs del pull-to-refresh de "Mis reservas" (rediseño de la entrada de abajo, nunca verificado en dispositivo real — ver su nota de "⚠️ Pendiente de confirmación"), encontrados en QA manual y esta vez sí verificados con Chromium real vía Playwright (`TouchEvent`/`Touch` sintéticos reales, no jsdom — el segundo bug es específicamente de timing de eventos táctiles). **(1) Círculo del spinner desfasado del centro de su fondo circular** (`css/estilos.css:107`, `.ptr-spinner`): sobreescribe `width`/`height`/`border-width`/`animation` de `.spinner`, pero no su `margin: 0 auto 16px` (`estilos.css:49`) — pensado para un spinner standalone con texto debajo, no para uno anidado en `.ptr-indicator-inner` (`display:flex;align-items:center;justify-content:center`, 36×36px). El `margin-bottom:16px` asimétrico hace que el flex centre la *caja de margen* del spinner en vez de su contenido, empujando el círculo 8px hacia arriba del centro real — medido directamente (`getBoundingClientRect()` del spinner vs. de `.ptr-indicator-inner`): `offsetVertical: -8px`, exactamente `16px / 2`. Fix: `margin: 0;` agregado a `.ptr-spinner` — verificado que el offset pasa a `0px`. **(2) El gesto quedaba permanentemente inutilizado por una sola muestra de `touchmove` con `delta<=0`** (`js/home.js:126`, listener `touchmove`): `if (delta <= 0) { _ptrArrastrando = false; _ptrOcultarIndicador(); return; }` no solo ocultaba el indicador ese frame — mataba el tracking del gesto entero mientras el dedo seguía apoyado, porque tanto `touchmove` como `touchend` arrancan con `if (!_ptrArrastrando) return;`. Y `delta<=0` es común, no un caso raro: alcanza con que la *primera* muestra de `touchmove` coincida con el punto exacto de `touchstart` (`delta=0`) para inutilizar el gesto completo desde el instante cero, sin importar cuánto arrastre después el usuario. Reproducido con una secuencia de arrastre de 160px con jitter realista (micro-fluctuaciones típicas de un dedo humano, incluyendo una muestra inicial en `delta=0`): `getReservasPersona` nunca se disparaba. Fix: se saca `_ptrArrastrando = false;` de esa rama, dejando solo `_ptrProgreso = 0; _ptrOcultarIndicador(); return;` — sigue ocultando el indicador visualmente si el dedo sube por encima del punto de inicio, pero sin matar el tracking; si el dedo retoma el arrastre hacia abajo, `touchmove` sigue funcionando, y `touchend` siempre refleja el último estado real. Verificado que la misma secuencia con jitter ahora sí dispara y completa el refresh (`_ptrRefrescando` vuelve a `false`, indicador oculto), y que el caso legítimo de cancelación (arrastra, sube por encima del punto de inicio, suelta ahí sin volver a bajar) sigue sin disparar un refresh — no se rompió ese comportamiento. No se tocó `_PTR_RANGO`/`_PTR_MAX_VISUAL`/la curva de resistencia/el backstop de 10s — nada de eso estaba involucrado en ninguno de los 2 bugs.
- **js/home.js** — Segundo problema relacionado encontrado en QA manual sobre "Volver a Mis Reservas" (entrada de abajo): con el fix anterior ya aplicado (spacer nunca en 8px), al tocar el botón desde `s6` con 0 reservas previas todavía aparecía brevemente un spinner "suelto" — sin la nav ni el label "MIS RESERVAS"/"Ver historial" arriba — que recién se completaba con el layout una vez que resolvía `getReservasPersona`; se percibía como 2 transiciones distintas en secuencia en vez de una sola instantánea. Diagnóstico verificado con capturas de pantalla cuadro a cuadro (Playwright, cada ~40ms) contra `index.html` real: se descartó que fuera `#loading-overlay` (su opacidad se mantiene en 0 durante todo el flujo, nunca llega a pintarse) y se descartó un doble-fade por CSS (`transition` del spinner + `animation:fadeIn` del contenido final) — la opacidad de `#home-reservas-lista` sube en una sola curva continua, sin caída intermedia. La causa real: `_sincronizarNavHome()` (fix anterior) solo decide si mostrar el nav **después** de que resuelve `getReservasPersona`, y ese round-trip de red es exactamente la ventana donde el spinner se ve sin nav/header — el mismo spinner "se completa" de golpe cuando el fetch resuelve, lo que se percibe como 2 loaders distintos. ## 6. Reglas globales del proyecto

### Colores
Todos los colores deben declararse como variables CSS en `css/colors.css`. Ningún archivo CSS, JS o HTML puede hardcodear un valor hex, rgb o rgba para el que exista variable equivalente disponible.  
**Excepción única:** valores pasados directamente a librerías JS que no interpretan CSS (ej: array de colores del confetti en `ui.js` L204).

### Clases CSS
Toda clase nueva debe definirse en el archivo CSS correspondiente a su sección:
- Antes de crear una clase nueva, verificar si ya existe una equivalente en `global.css` o en el CSS de la sección.
- Clases compartidas entre secciones → `global.css`.
- Clases específicas de una sección → CSS de esa sección (`login.css`, `home.css`, `reservas.css`, `perfil.css`, etc.).

### Estilos inline
Evitar estilos inline en HTML y en strings JS. Si un estilo se repite más de una vez, convertirlo en clase CSS.  
> Bug corregido: el patrón `color:color: var(...)` (prefijo duplicado en strings JS) fue detectado y corregido en `home.js` (L172, L173, L175) y `admin.js` (L372, L401).

### theme-color (barra de estado del sistema)
Todo HTML raíz nuevo (`index.html`, `inscripcion/index.html`, y cualquier sección futura con su propio HTML de nivel superior) debe declarar el par:
```html
<meta name="theme-color" content="{--bg dark}" media="(prefers-color-scheme: dark)">
<meta name="theme-color" content="{--bg light}" media="(prefers-color-scheme: light)">
```
con los valores exactos de `--bg` y `--bg` dark de `css/colors.css` (hoy `#FDF3EB` light / `#170900` dark), sincronizados **a mano** — `<meta>` no soporta `var()` CSS, así que no hay forma de que hereden el valor automáticamente. Si `--bg`/`--bg` dark cambian en `colors.css`, hay que actualizar el meta tag en cada HTML raíz manualmente (`colors.css` tiene comentarios junto a cada variable recordando esto).

**PWA instalada (barra de gestos de Android):** `manifest.json` (`background_color`/`theme_color`) controla el color de la barra de navegación gestual inferior del sistema cuando la app está instalada como PWA — es un mecanismo distinto al `<meta name="theme-color">` de arriba (que solo cubre la barra de estado superior). A diferencia del HTML, el spec de Web App Manifest **no soporta variantes por `prefers-color-scheme`**: `theme_color`/`background_color` son valores únicos y estáticos, así que se fijan al valor `--bg` **light** (`#FDF3EB`), igual que ya hacía `background_color`. Mismo criterio de sincronización manual con `colors.css` (comentario también agregado ahí). **Advertencia:** el soporte de Chrome/Android para que la barra de gestos respete `theme_color` en PWA instalada es inconsistente entre versiones — no está garantizado al 100% en todos los dispositivos; esto mejora la probabilidad, no la asegura.

### Navegación por gestos (pushState/popstate)
Todo flujo de pasos o pantallas nuevo (formularios multi-paso, wizards, secciones con "pantallas" internas) debe empujar su propio estado al historial del navegador, para que el gesto nativo de "atrás" (swipe back / botón atrás) retroceda un paso/pantalla a la vez en vez de saltar directo a la página anterior real. Patrón de referencia, `ir(id, desdeHistorial)` / `popstate` en `js/ui.js:81-150` (usado por toda la app principal) y replicado en `inscMostrarPaso(idx, desdeHistorial)` / `popstate` en `inscripcion/inscripcion.js`:
- La función que muestra el paso/pantalla acepta un segundo parámetro `desdeHistorial`; si es falsy, hace `history.pushState({...}, '', '#...')`.
- Un `history.replaceState(...)` inicial (fuera de esa función, a nivel de módulo) seedea el primer paso/pantalla como la entrada actual, sin agregar una entrada extra.
- Un listener `popstate` propio del flujo lee `ev.state` y vuelve a llamar a la función de mostrar-paso con `desdeHistorial=true` (para no re-empujar).
- Al estar en el primer paso/pantalla del flujo y volver a hacer "atrás", no hay más estados propios que consumir — el navegador sale de forma nativa a la página anterior real, sin intervención de JS.

**Pantallas raíz — el gesto de "atrás" debe ser un no-op, no un salto ni una salida:** a diferencia de lo anterior (donde "atrás" debe retroceder un paso), hay pantallas que son la raíz de su propio contexto y de las que no debería existir ningún "anterior" navegable dentro de la app — hoy `s1` (login, raíz sin sesión), `s-home` (Mis Reservas, raíz con sesión) y `s-admin-home` (raíz del panel admin), listadas en `PANTALLAS_RAIZ` (`js/ui.js`, junto a `TOP_BAR_CONFIG`). En estas pantallas, el gesto de "atrás" del sistema (swipe/botón) no debe navegar a ninguna otra pantalla **ni** salir de la app — el usuario se queda donde está (el único gesto que sí puede minimizar/cerrar la app es el swipe-up nativo de Android, que es un mecanismo del SO ajeno a esto). Mecanismo ("atrapar" el historial): cada vez que `ir(id, ...)` (`js/ui.js:81-...`) navega a una pantalla incluida en `PANTALLAS_RAIZ`, además del `pushState` normal empuja **un segundo `pushState` duplicado de sí misma** (salvo que se pase `sinTrampa=true` como tercer parámetro) — así, sea que se llegue por navegación hacia adelante (login exitoso) o por `popstate` (`ir(id, true)`), siempre queda un duplicado de la misma pantalla debajo en el historial real. El primer "atrás" hace que el navegador retroceda a ese duplicado (dispara `popstate`, nunca sale de la app sin pasar por JS), el listener de `popstate` (sin cambios de lógica) resuelve el mismo `id` raíz, lo re-renderiza (sin cambio visible) y `ir()` vuelve a empujar un duplicado fresco — el "piso" se auto-sostiene indefinidamente, cualquier cantidad de "atrás" queda atrapada. La siembra inicial de `s1` (`history.replaceState({pantalla:'s1'},...)`, fuera de `ir()`) tiene su propio duplicado sembrado a mano justo debajo, para que el primerísimo "atrás" (antes de cualquier interacción) ya quede atrapado. El tercer parámetro `sinTrampa` existe para el resync de `pageshow`/bfcache (`js/auth.js`, `window.addEventListener('pageshow', ...)`) — al restaurarse desde bfcache el historial real ya está intacto (el "piso" ya lo mantiene `ir()` desde antes de que la app pasara a segundo plano), así que ese resync solo necesita re-renderizar la pantalla activa sin tocar el historial en absoluto (ni el push normal ni el duplicado de trampa), evitando acumular entradas de más en cada ciclo de background/foreground. Efecto secundario esperado y aceptado: en sesiones muy largas se acumulan entradas de historial duplicadas para las pantallas raíz — inofensivo, sin impacto para el usuario, no requiere mitigación.

### Pull-to-refresh nativo
El pull-to-refresh nativo del navegador (reload completo de página al arrastrar hacia abajo estando arriba del todo) está deshabilitado globalmente vía `overscroll-behavior-y: contain` en `html, body` (`css/global.css`). Como `inscripcion/index.html` (y cualquier HTML raíz futuro que siga la convención de importar `colors.css` + `global.css`) hereda esta regla automáticamente, no hace falta repetirla por sección. Cualquier gesto de refresh custom (ej. el de "Mis reservas", ver `js/home.js`) se implementa scopeado a su sección específica — nunca reactivando el reload nativo del navegador.

### Despliegue (GitHub Pages) y su fallo intermitente conocido
El sitio se publica con GitHub Pages en modo "Deploy from a branch" (rama `main`) — **no existe ningún workflow propio en `.github/workflows/`**; el pipeline "pages build and deployment" que aparece en la pestaña Actions lo genera y corre GitHub internamente (`path: dynamic/pages/pages-build-deployment`, no es un archivo del repo, no hay nada ahí para editarle reintentos). Dominio custom vía el archivo `CNAME` en la raíz (`reservas.quindesvolcanicos.com`).

**Fallo intermitente conocido, no relacionado con el contenido del repo:** el job `deploy` (paso "Deploy to GitHub Pages") falla de forma esporádica con el mensaje genérico de GitHub `"Deployment failed, try again later."` — confirmado (vía la API de Actions, `gh` no está instalado en este entorno) revisando varios runs recientes fallidos de commits con contenido completamente distinto entre sí (CSS, JS, solo docs): en todos los casos el job `build` (Jekyll + upload de artifact) termina en éxito, y únicamente el paso final de publicación (llamada interna de GitHub al backend de Pages) falla, con el mismo mensaje genérico. Ocurrió en ~4 de los últimos 7 pushes distintos a `main` antes de este commit (incluido el commit `0efdae3`) — no es un caso aislado. Causa: inestabilidad del backend de despliegue de GitHub Pages (posiblemente agravada por el dominio custom), ajena al código del proyecto. **No hay ninguna acción de código que lo prevenga** (no hay workflow propio donde agregar `retry`); si un deploy falla con este mismo mensaje y el job `build` salió en verde, la única vía es forzar un run nuevo — un nuevo push a `main`, o re-ejecutar el job fallido a mano desde la pestaña Actions de GitHub.
